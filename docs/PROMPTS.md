# Промпты: устройство и принятые решения

Источник в коде — `src/prompts.py`. Ниже — полные тексты в том виде,
в котором их видит модель (числовые ограничения подставляются из
констант `src/models.py`, поэтому текст не может разойтись с
pydantic-валидацией).

## 1. Системный промпт (полный текст)

```text
Ты — ассистент контент-менеджера B2B-магазина контрольно-измерительных
приборов. По входным данным готовишь черновик карточки товара:
SEO-заголовок, SEO-описание, характеристики, поисковые запросы и
коммерческий блок.

ЖЁСТКИЕ ПРАВИЛА (нарушение любого делает ответ непригодным):
1. Используй только факты из входных данных. Запрещено выдумывать числа,
единицы, диапазоны, классы точности, интерфейсы и любые технические
характеристики.
2. Если характеристика отсутствует во входных данных — выведи её в списке
характеристик со значением «данных нет».
3. Язык вывода — русский.
4. SEO-заголовок — не более 70 символов.
5. SEO-описание — строго от 800 до 1200 символов: осмысленное, без воды, без
маркетинговых преувеличений о технических параметрах.
6. Поисковых запросов — от 3 до 5.
7. Коммерческий блок — кратко: кому подходит прибор и какие задачи он
решает (для менеджера по продажам).
8. Не ссылайся на несуществующие стандарты, сертификаты, ГОСТы — только
на те, что названы во входных данных.

Ответ верни строго в формате JSON по схеме из сообщения пользователя:
без markdown-обёрток, без пояснений и любого текста вокруг JSON.
```

## 2. Пользовательский промпт (шаблон и полный пример)

Формируется функцией `build_user_prompt(product, missing_fields)`.
Структура — структурированная подача входа с чёткими разделителями,
чтобы модель не путала поля. Блок «ОТСУТСТВУЮЩИЕ ХАРАКТЕРИСТИКИ»
появляется, если валидатор входа (`src/validator.py`) нашёл ожидаемые,
но отсутствующие характеристики, — так правило «модель обязана вывести
их как „данных нет"» доходит до модели явно.

Полный пример (вход `examples/testo_510_input.json`):

```text
Сформируй черновик карточки товара по данным ниже.

НАЗВАНИЕ: Дифференциальный манометр testo 510
ПРОИЗВОДИТЕЛЬ: Testo
КАТЕГОРИЯ: Измерители давления воздушного потока

ХАРАКТЕРИСТИКИ (используй только их; отсутствующие пометь «данных нет»):
Диапазон измерений: 0…100 гПа
Погрешность: ±0,03 / ±0,05 / ±(0,1 гПа + 1,5 %)
Разрешение: 0,01 гПа
Перегрузка: 500 мбар
Макс. статическое давление: 1,5 бар
Частота измерений: 0,5 с
Единицы измерения: гПа, мбар, Па, мм вод.ст., psi, м/с и др.
Степень защиты: IP40
Питание: 2×ААА
Ресурс батареи: 50 ч
Габариты: 119×46×25 мм
Рабочая температура: 0…+50 °C
Вес: 90 г
Гарантия: 2 года

ОТСУТСТВУЮЩИЕ ХАРАКТЕРИСТИКИ (обязательно выведи каждую в specs со значением «данных нет»): интерфейсы

ОПИСАНИЕ (источник фактов):
Дифференциальный манометр testo 510 предназначен для измерения перепада
давления воздуха. Диапазон измерений — 0…100 гПа, погрешность — ±0,03,
±0,05 или ±(0,1 гПа + 1,5 %), разрешение — 0,01 гПа. Прибор выдерживает
перегрузку 500 мбар и максимальное статическое давление 1,5 бар; частота
измерений — 0,5 с. Поддерживаются единицы: гПа, мбар, Па, мм вод.ст.,
psi, м/с и другие. Корпус защищён по IP40, питание — 2×ААА с ресурсом
до 50 ч, рабочая температура — 0…+50 °C. Габариты — 119×46×25 мм,
вес — 90 г, гарантия — 2 года.

Верни СТРОГО JSON по схеме:
{
  "seo_title": "строка, не более 70 символов",
  "seo_description": "строка от 800 до 1200 символов",
  "specs": [
    {"name": "название характеристики",
      "value": "значение из входа или «данных нет»"}
  ],
  "search_queries": ["от 3 до 5 поисковых запросов"],
  "commercial_block": "кому подходит прибор и какие задачи решает",
  "missing_fields": ["характеристики, которых нет во входных данных"]
}
```

## 3. Обоснование каждого правила

| Правило | Почему именно так |
|---|---|
| 1. Только факты из входа | Карточка идёт в B2B-каталог: неверное число в характеристиках — возврат товара, претензии и репутационный риск. Модель склонна «дорисовывать» правдоподобные значения, поэтому запрет сформулирован перечислением типов данных (числа, единицы, диапазоны, интерфейсы), а не общей фразой. |
| 2. «данных нет» | Явно разрешённый способ сказать «не знаю». Без него модель чаще выдумывает значение, чем оставляет дыру; со значением-маркером пропуск становится легальным выходом и виден менеджеру. |
| 3. Русский язык | Аудитория и площадка — русскоязычный B2B-магазин; LLM на русских входных данных может соскальзывать в английские термины. |
| 4. Заголовок ≤ 70 символов | Требование задания; типичный лимит сниппета поисковой выдачи — длиннее обрезается. |
| 5. Описание 800–1200 символов | Требование задания: достаточно для SEO и без «простыни». «Без преувеличений о параметрах» — вторая линия той же защиты, что правило 1: маркетинговый текст не должен подменять технические факты. |
| 6. Запросов 3–5 | Требование задания: мало — нет покрытия, много — размывается семантика и растёт риск нерелевантных запросов. |
| 7. Коммерческий блок для менеджера | Задача блока — «кому продаём и что решаем», а не техпаспорт; отделён от описания, чтобы описание оставалось SEO-текстом. |
| 8. Никаких выдуманных ГОСТов/сертификатов | Отдельно выделено, потому что для КИП это самый дорогой вид галлюцинации: ссылка на несуществующий ГОСТ дискредитирует поставщика. Число из номера ГОСТа верификатор дополнительно ловит кодом. |
| JSON без markdown-обёрток | Модель любит ```json-обёртки и пояснения; парсер умеет их срезать, но явный запрет уменьшает долю ретраев. |

## 4. Уточняющий промпт повтора (RETRY_PROMPT)

Используется генератором (`src/generator.py`) ровно один раз: при
невалидном JSON, несоответствии схеме или выдуманных числах в
SEO-описании. `{reason}` — конкретная причина отказа, поэтому вторая
попытка точечная, а не «попробуй ещё раз»:

```text
Твой предыдущий ответ не принят: {reason}
Верни ответ ещё раз: строго валидный JSON по той же схеме, без markdown-обёрток и пояснений. Исправь указанную проблему, остальное сохрани без изменений. Все числа бери только из входных данных.
```

## 5. Верификатор: почему он нужен сверх промпта

Промпт — это просьба; код — гарантия. Даже идеально сформулированные
правила модель может нарушить (длина описания, правдоподобное «0,5 гПа»
вместо «0,01»). Поэтому `src/verifier.py` проверяет каждый ответ:

1. Из ответа LLM (значения specs + seo_description) регэкспом
   извлекаются все числа с ближайшей единицей (`0,03 гПа`, `9 В`, `5 %`).
2. Единицы распознаются по белому списку (Па/бар/мм/°C/%/В/А/Ом/Гц/кг/л…);
   обычные слова рядом («от 0 до 100», «510 измеряет») единицами не
   считаются.
3. Каждое число ищется в полном тексте входа (название, производитель,
   категория, характеристики, описание) с нормализацией: `0,03 ≡ 0.03`;
   `0...100 ≡ 0–100 ≡ 0 - 100` (диапазон распадается на концы);
   `гПа ≡ ГПа ≡ hPa` (кириллица транслитерируется, алиасы `гц≡Hz`,
   `ч≡h`, `Вт≡W`, `Ом≡Ω`); число с единицей требует, чтобы единица тоже
   была во входе — «100 МПа» против входа «0...100 гПа» отклоняется.
4. Итог — отчёт со счётчиками проверенных/отклонённых чисел и списком
   нарушений с контекстом (п. 6.4.4 плана — прозрачность; сводка
   печатается CLI в stderr и входит в `GenerationResult`).

Дальше работает генератор: выдуманное число в specs → значение
заменяется на «данных нет» (п. 6.4.3 «удаление»); в seo_description →
одна перегенерация с причиной («повторная генерация»); остались и
после неё → ошибка без карточки. Инвариант: **в возвращаемой карточке
нет ни одного числа, которого нет во входных данных**.

Реальный кейс: при генерации примеров (этап 12) обе карточки YandexGPT
приняты со второй попытки — ретрай по причине из верификатора/схемы
сработал в бою; финальные отчёты: «Проверено чисел: 36, отклонено: 0»
(testo 510) и «Проверено чисел: 48, отклонено: 0» (ИМС-Ф1).

## 6. Принятые решения

| Параметр | Значение | Почему |
|---|---|---|
| Модель | `yandexgpt` (последняя стабильная) | Основной провайдер по заданию, сильный русскоязычный контент. Резерв — любой OpenAI-совместимый (`LLM_PROVIDER=openai_compatible`). |
| Температура | 0.2 (`LLM_TEMPERATURE`) | Фактовый, а не творческий текст: низкая температура уменьшает выдумывание и разброс формулировок между запусками. |
| max_tokens | 2000 (`LLM_MAX_TOKENS`) | Карточка ~700–900 токенов; запас на ретрай внутри одного ответа без риска обрезки (обрезанный JSON = битый ответ). |
| Таймаут | 60 с (`LLM_TIMEOUT`) | Генерация 800–1200 символов укладывается; меньше — ложные таймауты, больше — долгий висящий запрос. |
| Ретраи HTTP | до 3 попыток, только 429/5xx, backoff 1–2–4 с | Таймауты и 4xx не повторяются (бессмысленно/опасно); детали — `src/llm/base.py: run_with_retries`. |
| Ретрай контента | ровно 1 повтор на битовую схему ИЛИ выдуманные числа в описании, общий бюджет 2 попытки | По п. 6.3 «одна повторная попытка, затем понятная ошибка»; расширение на верификацию описания — п. 6.4.3. |
| Формат вывода | строгий JSON + pydantic-схема | Машиночитаемость для API и CMS; ограничения длин (70/800–1200/3–5) зашиты в схему, поэтому нарушение длин — это невалидный ответ, а не «почти хорошо». |
