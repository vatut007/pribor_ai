# План реализации: AI-помощник для подготовки товарных описаний

> Самодостаточный документ для агента-исполнителя. Содержит всё необходимое: постановку задачи, зафиксированные решения, данные, архитектуру, требования к промптам, чек-лист сдачи и критерии приёмки. Дополнительных вопросов к заказчику не требуется — все ключевые решения уже приняты.

---

## 1. Постановка задачи (что строим)

Прототип сервиса: на вход подаются данные о контрольно-измерительном приборе в JSON, сервис обращается к LLM через API и формирует **черновик карточки товара для B2B-интернет-магазина**.

**Что сервис обязан выдать на каждый товар:**

| Блок | Требование |
|---|---|
| SEO-заголовок | до 70 символов |
| SEO-описание | 800–1 200 символов |
| Структурированный список ключевых характеристик | из входных данных |
| Поисковые запросы | 3–5 шт., под которые оптимизируется страница |
| Commercial-блок | кому подходит прибор и какие задачи решает — коротко для менеджера |

**Жёсткие ограничения (за нарушение режется оценка):**

- LLM **не должна выдумывать характеристики** — все технические значения берутся только из входных данных;
- если характеристики нет — в результате пишется «данных нет» (или аналог);
- API-ключи только в переменных окружения, `.env` в `.gitignore`;
- корректная обработка ошибок API, пустых полей и некорректного входного JSON;
- сдаётся Git-репозиторий + README + примеры для 2 товаров + описание промптов + список ограничений.

**Что НЕ делается** (по п. 8 задания): полноценная CMS, админ-панель, база данных, деплой, векторная база. Достаточно локального прототипа.

**Ориентировочное время:** 2–4 часа (план рассчитан на ~2,5–3 ч).

## 3. Данные (важная находка — обязательно учесть)

### 3.1. Про фид

Фид `souz-pribor.ru/yml/any/feed.xml` содержит **49 188 товаров**, но в нём **нет описаний и характеристик**: у каждой позиции только `name`, `typePrefix`, `vendor`, `vendorCode`, `price`, `currencyId`, `picture`, `url` и 2 служебных параметра («Артикул», «Код товара»). Структура входа из задания (`name`, `manufacturer`, `specs`, `description`) **невозможна из одного фида**.

**Решение:** выбрать 2 товара из фида и обогатить их данными с реальных страниц `souz-pribor.ru` (по полям `<url>`). Проверено: страницы содержат описание (1 600–2 500 символов) и таблицу характеристик (15–20 строк реальных данных). Входные JSON формируются строго из фактов со страниц.

### 3.2. Выбранные товары

| # | Товар | Производитель | Категория | URL страницы | id в фиде |
|---|---|---|---|---|---|
| 1 | Дифференциальный манометр testo 510 | Testo | Измерители давления воздушного потока | `https://www.souz-pribor.ru/product/testo-510/` | 58444 |
| 2 | Мультиметр ОВЕН ИМС-Ф1 | ОВЕН | Измерители параметров электрической сети | `https://www.souz-pribor.ru/product/ims-f1/` | 58787 |

Выбор обоснован: testo 510 близок к примеру из задания (манометр), ИМС-Ф1 — другая категория (электрические измерения), оба дают богатые реальные характеристики.

### 3.3. Ключевые реальные характеристики (для входных JSON)

**testo 510:** диапазон 0…100 гПа; погрешность ±0,03 / ±0,05 / ±(0,1 гПа + 1,5 %); разрешение 0,01 гПа; перегрузка 500 мбар; макс. статическое давление 1,5 бар; частота измерений 0,5 с; единицы (гПа, мбар, Па, мм вод.ст., psi, м/с и др.); IP40; питание 2×ААА; ресурс 50 ч; габариты 119×46×25 мм; рабочая температура 0…+50 °C; вес 90 г; гарантия 2 года.

**ОВЕН ИМС-Ф1:** напряжение 40…400 В; ток 0,02…5 А; активная/реактивная/полная мощность 0,02…2,000 (кВт/кВАр/кВА); частота 43…63 Гц; cos φ 0…1,000; погрешность ≤0,1 %; питание 90…264 В / 47…63 Гц; потребление ≤6 ВА; 2 входа; время опроса ≤1 с; IP54; габариты 96×96×65 мм; масса ≤0,5 кг; срок службы 10 лет; рабочая температура −20…+50 °C; ГОСТ Р 51522-99; внесён в Госреестр СИ.

> Любое число в выходной карточке должно быть взято из этого списка. Верификатор проверяет это программно (см. п. 6).

### 3.4. Демонстрация обработки недостающих данных

Входы должны быть реалистичными, с естественными пропусками, чтобы продемонстрировать поведение «данных нет»:

- testo 510: «класс точности» в явном виде отсутствует (есть погрешность), «цифровой интерфейс» не задокументирован → в карточке эти поля должны выйти как «данных нет».
- ИМС-Ф1: «класс точности» как число отсутствует (есть погрешность 0,1 %), «подключение» описано частично → пропуски помечаются явно.

Не нужно искусственно удалять реальные поля — пропуски берутся из естественных «дыр» в данных страницы.

## 5. LLM-слой (OOP, расширяемый)

### 5.1. Абстракция

`src/llm/base.py`:

- `@dataclass LLMMessage` — поля `role` (`system`/`user`/`assistant`), `content`.
- `@dataclass LLMResponse` — поля `text`, `model`, `usage` (опц.), `raw` (опц.).
- `class BaseLLMClient(ABC)`:
  - абстрактный `chat(messages: list[LLMMessage], *, temperature: float, max_tokens: int, timeout: float) -> LLMResponse`;
  - `health() -> bool` — лёгкая проверка наличия конфига/ключей;
  - единая обёртка ошибок: таймаут, сетевая ошибка, лимиты запросов, невалидный ответ — всё оборачивается в доменные исключения (`LLMError`, `LLMTimeoutError`, `LLMRateLimitError`, `LLMResponseError`).

### 5.2. YandexGPTClient (первичный)

- Endpoint: `POST https://llm.api.cloud.yandex.net/foundationModels/v1/completion`.
- Авторизация: заголовок `Authorization: Api-key <YC_API_KEY>` **или** `Bearer <YC_IAM_TOKEN>` + заголовок `x-folder-id: <YC_FOLDER_ID>`.
- `modelUri = gpt://<YC_FOLDER_ID>/yandexgpt` (модель `yandexgpt`; lite-вариант `yandexgpt-lite` — опционально).
- Маппинг `LLMMessage[]` → формат YandexGPT (`messages: [{role, text}]`, `completionOptions: {stream, temperature, maxTokens}`).
- Парсинг ответа: `alternatives[0].message.text`; обработка пустого ответа и ошибок API (HTTP-код → доменное исключение).
- HTTP через `requests` (или `httpx`); ретраи с экспоненциальным backoff на 429/5xx (макс. 3 попытки).

### 5.3. OpenAICompatibleClient (резервный)

- Работает с любым OpenAI-совместимым endpoint: OpenAI, DeepSeek, локальные (Ollama, vLLM, LM Studio) через `LLM_BASE_URL`.
- Конфиг: `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`.
- Endpoint: `POST {LLM_BASE_URL}/chat/completions`, стандартный формат OpenAI.

### 5.4. Factory

`src/llm/factory.py` → `get_client() -> BaseLLMClient`:
- читает `LLM_PROVIDER` из env (`yandexgpt` | `openai_compatible`);
- выбирает и инстанцирует провайдер, валидирует наличие нужных env-переменных (иначе понятная ошибка);
- **добавить своего провайдера** = унаследовать `BaseLLMClient`, реализовать `chat()`, добавить ветку в factory. Это и есть расширяемость, запрошенная заказчиком.

## 6. Промпты и защита от галлюцинаций (центр оценки)

### 6.1. Системный промпт

Роль: «ассистент контент-менеджера B2B-магазина контрольно-измерительных приборов».

Жёсткие правила (явно в промпте):
1. Используй **только** факты из входных данных. Запрещено выдумывать числа, единицы, диапазоны, классы точности, интерфейсы и любые технические характеристики.
2. Если характеристика отсутствует во входе — выведи её в списке со значением «данных нет».
3. Язык вывода — русский.
4. SEO-заголовок — не более 70 символов.
5. SEO-описание — строго 800–1 200 символов, осмысленное, без воды, без маркетинговых преувеличений о технических параметрах.
6. Поисковых запросов — от 3 до 5.
7. Commercial-блок — кратко: кому подходит прибор и какие задачи решает (для менеджера по продажам).
8. Не ссылайся на несуществующие стандарты, сертификаты, ГОСТы, не названные во входе.

### 6.2. Пользовательский промпт

Структурированная подача входа с чёткими разделителями (чтобы модель не путала поля). Пример:

```
Сформируй черновик карточки товара по данным ниже.

НАЗВАНИЕ: <name>
ПРОИЗВОДИТЕЛЬ: <manufacturer>
КАТЕГОРИЯ: <category>

ХАРАКТЕРИСТИКИ (используй только их; отсутствующие пометь «данных нет»):
<спецификации в виде ключ: значение>

ОПИСАНИЕ (источник фактов):
<description>

Верни СТРОГО JSON по схеме:
{ "seo_title": ..., "seo_description": ..., "specs": [...], "search_queries": [...], "commercial_block": ... }
```

### 6.3. Структура вывода (строгий JSON)

Pydantic-модель `ProductCardOutput`:
```python
class SpecItem(BaseModel):
    name: str
    value: str          # значение из входа ИЛИ "данных нет"

class ProductCardOutput(BaseModel):
    seo_title: str              # len <= 70
    seo_description: str        # 800 <= len <= 1200
    specs: list[SpecItem]
    search_queries: list[str]   # 3 <= len <= 5
    commercial_block: str
    missing_fields: list[str]   # список отсутствующих характеристик
```

Парсинг ответа LLM:
- извлечь JSON из ответа (модель может обернуть в ```json```);
- валидация через pydantic; при невалидном/обрезанном ответе — одна повторная попытка с уточняющим промптом, затем понятная ошибка.

### 6.4. Верификатор (анти-галлюцинация кодом, не «надежда на промпт»)

`src/verifier.py` — после получения ответа LLM:
1. Извлекает все числовые значения и единицы из `specs` и `seo_description` (regex по числам + ближайшим единицам).
2. Каждое найденное число проверяет на присутствие во входных данных (с нормализацией форматов: `0,03` ≡ `0.03`, `0...100` ≡ `0–100` ≡ `0 - 100`, единицы `гПа` ≡ `ГПа` ≡ `hPa`).
3. Числа, отсутствующие во входе → помечаются как `HALLUCINATED`; они либо удаляются из вывода с заменой на «данных нет», либо (при критичных расхождениях) запускается повторная генерация.
4. Готовит отчёт верификации (сколько чисел проверено, сколько отклонено) — для прозрачности.

Верификатор — это главное отличие «качественного решения» от «работает на удачу»: даже если модель ослушается промпта, код не пропустит выдуманное число в финальную карточку.

### 6.5. Валидатор входа

`src/validator.py`:
- проверка структуры (pydantic): обязательные `name`, `manufacturer`; `specs` — dict; `description` — строка;
- некорректный JSON → понятная ошибка с указанием позиции;
- пустые поля → отчёт `missing_fields`;
- список «ожидаемых характеристик» (диапазон, класс точности/погрешность, питание, тип корпуса/защиты, интерфейсы, габариты) — если каких-то нет, они попадают в `missing_fields` и модель обязана вывести их как «данных нет».

## 7. FastAPI и CLI

### 7.1. FastAPI (`app.py`)

- `POST /generate` — тело: JSON товара (по схеме `ProductInput`); ответ: `ProductCardOutput` (+ опционально `?format=md` возвращает Markdown).
- `GET /` — отдаёт `templates/form.html`: форма с текстовым полем для JSON (или отдельные поля name/manufacturer/specs/description), кнопка «Сгенерировать», результат в соседнем блоке с кнопкой «Копировать». Без JS-фреймворков, минималистично, inline-стили.
- Обработка ошибок: 422 для некорректного входа, 502/503 для ошибок LLM, понятные сообщения.
- Запуск: `uvicorn app:app --reload`.

### 7.2. CLI (`main.py`)

```
python main.py <input.json> [--format json|md] [--output <path>]
```
- читает входной файл, валидирует, генерирует карточку, печатает в stdout или пишет в `--output`.
- `--provider yandexgpt|openai_compatible` — переопределение провайдера.

## 9. Примеры результатов для 2 товаров (п. 6 задания)
